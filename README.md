# spec-check

A gate for the record a change carries about itself. It reads a commit message, a pull
request body or a spec file, and fails when the facts a reviewer needs are missing.

It judges **presence of facts, never style**. Terse prose and verbose prose carrying the same
facts both pass. A paragraph of filler fails and names the slot it is missing.

```
feat(ui): the map is the link, text link goes

Why: the answer carried a picture and a blue link to the same place.
Rule: the image src is never model-supplied; the url goes through the _url allowlist.
Verified: 390x844, hostile url drew unlinked, 0 off-origin images. Suite: 1067 passed.

Spec: docs/specs/2026-11-14-tappable-map.md
```

## Why it exists

One failure shape, over and over: the record of a change did not carry the fact that would
have caught the mistake.

- A capability is built, tested and merged **inert**, because nothing asks what makes it
  reachable.
- An incident is written down, and the writing is mistaken for the fix.
- A green tick means "the job ran" rather than "somebody looked".

A completion claim with no evidence attached is the thread running through all three. Git
history had no gate for it: a commit can claim anything, and `Verified:` shows up in some
bodies and not others.

## The rules

prose around it is hand written; the block is not.

**Tiers.** The tier is computed from the paths a change touches (`spec-check tier` prints it
and names the source of the list it used).

| Tier | Slots required | Needs |
|---|---|---|
| 0 | `Spec:` | a `Spec: none (<reason>)` trailer |
| 1 | `Why:`, `Rule:`, `Verified:`, `Spec:` | Why/Rule/Verified in the message, which is the spec |
| 2 | `Why:`, `Rule:`, `Verified:`, `Spec:` | a spec file, named in a `Spec:` trailer |

**Tier 0** is a change touching only these, the class whose mistakes announce themselves the
next time somebody runs the thing: `app/prompts/*`, `docs/*`, `*.md`, `LICENSE`, `.gitignore.example`. **Tier 2** is anything matching the list below.
**Tier 1** is everything else.

**Slots.** Content is judged by presence of facts, never length or wording: a slot must carry
at least 3 words and must not repeat the subject. A subject is capped at
72 characters.

| Slot | Holds |
|---|---|
| `Why:` | what was **observed**, not what was feared |
| `Rule:` | the invariant that is true now |
| `Cost:` | the trade that was accepted, if any |
| `Verified:` | the command and its result |
| `Rejected:` | what was turned down, and why |
| `Spec:` | a path, `in-message`, or `none (<reason>)` |

`Verified: not run (<reason>)` is accepted, is never reported as verified, and cannot pass a
tier-2 change.

**A relative date needs an anchor.** A message saying `yesterday`, `last week` or `three days
ago` with no absolute date anywhere names a moment only in relation to when it was typed, and
fails. One date in the message is enough to satisfy it. Durations (`for three days`, `a
2-minute tick`) are spans rather than positions and are never flagged.

**The tier-2 list is the UNION of two sources**, never a precedence order: `.spec-tier2` in
the repository root, and the `paths:` block of a review workflow (default `.github/workflows/code-review.yml`). The
checker runs against the pull request's own checkout, so the branch supplies the
configuration; a union means a file in the branch can only ever make MORE paths tier 2.

Where a repository names neither, these built-in defaults apply: `.github/workflows/**`, `.github/actions/**`, `.env*`, `**/.env*`, `.gitignore`, `Dockerfile*`, `**/Dockerfile*`, `docker-compose*.yml`, `deploy/**`, `infra/**`, `terraform/**`, `*.tf`, `**/auth*.py`, `**/*_auth.py`, `**/config.py`, `**/settings.py`, `**/secret*`, `**/credential*`, `**/iam*`.

**A spec file** needs the front-matter keys `id`, `tier`, `status`, `quiet`, `paths` and the
sections `Problem`, `Invariants`, `Blast radius`, `Verification`, `Rejected`. Every numbered invariant `Sn` in
Invariants needs a row naming it in Verification: a test, a command with its result, or
`manual:` with what was done and what was seen.

**A spec path outside the repository** is accepted unvalidated only under a prefix the
deployment configures in `SPEC_EXTERNAL_PREFIX`, and fails as a missing file otherwise.

Exit codes: `0` pass, `1` fail with the missing slot named, `2` the tool could not run.
<!-- /spec-check:rules -->

A slot that repeats the subject, or says fewer than three words, fails: the diff already says
what changed.

## The spec file

Five required sections and five front-matter keys.
[`examples/SPEC-TEMPLATE.md`](examples/SPEC-TEMPLATE.md) is the template, and the test suite
validates that file, so the example cannot drift from the rule.

The mechanism worth understanding: **every invariant needs a verification row.** An invariant
with no test, command or `manual:` observation against it fails the check. That is the same
rule as refusing a completion claim with no evidence, applied to the design rather than to
the commit.

## Use it in CI

```yaml
name: Spec gate
on:
  pull_request:
    types: [opened, synchronize, reopened, edited, ready_for_review]

jobs:
  spec-gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 0          # the tier needs the base branch in the clone
      - uses: lacrx/spec-check@<commit-sha>
        with:
          body-file: ${{ runner.temp }}/pr-body.txt
          title: ${{ github.event.pull_request.title }}
          base: ${{ github.event.pull_request.base.ref }}
```

Write the body to a file through the **environment** first. A pull request title or body is
attacker-controlled text, and `${{ }}` inside a `run:` block is substituted before bash sees
the line, so a backtick in a body would execute on the runner:

```yaml
      - env:
          BODY: ${{ github.event.pull_request.body }}
        run: printf '%s' "${BODY:-}" > "${{ runner.temp }}/pr-body.txt"
```

Pin the action to a **commit sha**, not a tag or a branch. A tag can move.

`edited` belongs in the trigger list: the body is the record, and a body edited after the run
would otherwise keep a green tick earned by text that is no longer there.

## Use it locally

```bash
spec_check.py tier                        # what tier this change is, and why
spec_check.py rules --markdown            # the rules above, generated
spec_check.py docs --check CLAUDE.md      # is the generated block in that file current
spec_check.py docs --write CLAUDE.md      # make it current
spec_check.py msg .git/COMMIT_EDITMSG --warn
spec_check.py spec docs/specs/my-spec.md
spec_check.py pr --body-file body.txt --title "..."
spec_check.py --selftest                  # the cases that prove the rules
```

A `commit-msg` hook wants `--warn`: it reports and exits 0. Mid-branch commits are where a
thought is still moving, and a hook that hard-fails buys nothing except the `--no-verify`
habit. Fail at the pull request instead.

The exit codes are in the generated block above. The third one is the one worth knowing: a
tool error is `2`, never `1`, because a tool error must never read as a verdict.

## Documentation that cannot rot

A rule restated in prose is a rule that can rot, and when it rots nothing goes red: the code
changes, the sentence keeps its confident present tense, and the next reader believes
whichever copy they found first. Three such sentences shipped in one change here, each found
by a reviewer and none by any check.

Two directives, both meant for files an agent edits:

- **A generated block.** Mark a region of the file with an opening and a closing
  `spec-check:rules` HTML comment -- the exact pair is at the top of this README, under
  **The rules, generated** -- and `docs --write <file>` fills everything between them from
  the constants this tool enforces. `docs --check` is the gate: it fails when the block has
  drifted, which is how a consumer's restatement of these rules goes red the moment they
  move.

  **The pair is deliberately not written out in this bullet.** It was, until 2026-11-16, and
  `sync_blocks` replaces *every* block it finds -- so the illustration was itself a block,
  and `docs --write` injected the full rules table into the middle of this sentence. The
  README then carried two copies of the rules, which `docs --check` happily called current
  because both matched, and the duplication this tool exists to prevent sat in its own
  documentation for as long as nobody regenerated it. Found when a rule was added and the
  new paragraph appeared twice.
- **A claim tag.** `<!-- claim: some-tag -->` marks a sentence as checkable.
  `docs --claims <file>` prints the tags, for a consumer's own test suite to map each one to
  an assertion about that repository. The tool does not know what the claim means; it only
  makes the set of claims machine-readable, so a test can insist every tag has an assertion
  and every assertion still has a tag.

A file named on the command line with no generated block **fails**: a gate configured to
check a file that describes nothing is a gate reporting on nothing.

## Requirements

Python 3.9 or newer, standard library only. No install step, no dependencies, no network.
